**1. Blocking — item 25 puts the PAT inside a serialized, persisted model.** The plan has the sandbox spec carry `ForgejoCloneConfig { instance_url, token }`. But the sandbox/run-spec models are serde-serialized and persisted: `fabro_types::RunSpec` is embedded in `RunProjection` (the SQLite summary store's persisted projection — see `run_files.rs:2378` fixture and the recent "run projection replay" commits), and `RunSandbox` round-trips through serde with `clone_origin_url` (`fabro-types/tests/sandbox_model_serde.rs`). The GitHub path deliberately keeps credentials **out** of these models: tokens live in the runtime credential layer (`push_credentials.rs`, `InstallationTokenSource`, `GitHubCredentials` held by the provider/pipeline) and are embedded only into the clone URL / remote `set-url` handed to the container process. Putting a static PAT in the spec would write it into persisted run projections — a regression against `docs/internal/server-secrets-strategy.md` and the redaction/scrubbing machinery (which knows `FORGEJO_TOKEN` as an env name, not as an opaque spec field), and it would have to be reworked once review caught it. Fix: the spec carries only classification data (`instance_url`, or provider + origin); the token flows through the runtime credential layer exactly as item 26 already implies for push — items 25 and 26 currently contradict each other's premise.

**2. Concrete audit miss — `lib/apps/fabro-cli/src/shared/repo.rs` (`ensure_matching_repo_origin`).** It normalizes the local checkout's origin with `fabro_github::normalize_repo_origin_url` and string-compares against the run's expected origin before fork/resume actions. That normalizer is github.com-specific and will not convert a Forgejo SSH remote (`git@forgejo.example:owner/repo.git`) to HTTPS, so forking or resuming a run from a correct Forgejo SSH checkout fails with "does not match run repository". The plan's audit lists (item 23 for the workflow crate, item 38 for `runner.rs`) don't include this file. Fix: add it to the audit with provider-aware normalization (the instance-host-aware `normalize_origin_url` from the new crate). Not the same concern as round one — that was a missed *settings* coupling; this is a missed *CLI guard* that ships broken fork/resume for the tier-(a) surface.
