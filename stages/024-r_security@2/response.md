Security review complete. I read the full diff (111 files) and the surrounding context of every security-relevant seam: the new `fabro-forgejo` client, URL/host classification, credential embedding, clone-source construction, server handlers, config resolution, persistence, and the migration.

## Verdict

**No high- or medium-severity security defects found.** The change is careful at every seam where the new PAT touches a dangerous sink. One low-severity hardening finding, plus one inherent design exposure that is documented but worth restating.

## Findings

**1. LOW — TOML value injection in `forgejo_scm_block`** — `lib/apps/fabro-cli/src/commands/repo/init.rs` (new `forgejo_scm_block`). Owner/repo are parsed from the checkout's `git remote get-url origin` and interpolated into `.fabro/project.toml` via `format!("...owner = \"{owner}\"\nrepository = \"{repo}\"\n")` with no escaping or grammar validation. The SCP-like spelling `git@host:owner/repo` is split on `:` with no character restriction, so a remote URL containing `"` or newlines produces broken or attacker-shaped TOML. **What an attacker does / gets:** a victim must clone a repository whose origin URL the attacker chose *and* run `fabro repo init` inside it. Because the generated block only emits when the origin matches the configured instance, and real Forgejo owner/repo names are `[A-Za-z0-9._-]`, the practical impact is a corrupt `project.toml` (config load fails) or overriding `[run.scm]` keys in a file the same user could edit anyway — not code execution. Fix: validate owner/repo against the slug grammar (or build the TOML with a serializer) before writing.

**2. DESIGN OBSERVATION — static, instance-wide PAT readable inside the untrusted sandbox.** The clone embeds the PAT in the container's `origin` remote for the whole run (`docker.rs` post-clone `set-url`, same mechanism as GitHub), so any code the run executes can read `.git/config` and exfiltrate a **non-expiring** credential whose scope spans every repo the operator granted on the instance — unlike GitHub's short-lived, repo-scoped installation tokens. This is inherent to the human-approved PAT-only auth decision, not an implementation bug, and the shipped docs explicitly say "Scope it to the repositories it needs." No code change requested; flagging so the operational caveat stays visible.

**3. INFORMATIONAL — `normalize_origin_url` fallback keeps userinfo on `http://` origins** (`fabro-forgejo/src/url.rs`): `strip_credentials` handles only `https://`, so a credential-bearing `http://user:pass@instance/...` origin that falls to the fallback path (instance host match but malformed path) survives normalization. I traced every caller: reachable values are the user's own credentials, and the fallback requires a hand-crafted remote; it exactly mirrors the pre-existing GitHub `strip_https_credentials` behavior. Parity, not a regression.

## Verified safe (checked directly, not assumed)

- **No SSRF with the PAT.** The instance base URL comes only from operator config (`server.integrations.forgejo.url`); every forgejo dispatch (`load_pull_request_forgejo_context`, materializer, sandbox, diagnostics) resolves the context from settings. Stored PR-link origins must match the configured instance *before* any token-authenticated call, so a user-supplied link URL can never aim the deployment PAT at an arbitrary host. Link parsing rebuilds origin from scheme/host/port only — embedded credentials in a linked URL are stripped before persisting.
- **Host matching is URL-parsed, not substring.** `origin_matches_instance` compares parsed host (case-insensitive) plus effective port; `https://instance.evil.com` or port variants don't spoof a match.
- **No path traversal.** Sandbox layout components pass a strict ASCII allowlist rejecting `.`/`..`/`%2e%2e`; clone/fetch/checkout commands all use `shell_quote`, `--` separators, and validated branch/tag/SHA grammars; `SandboxSpec` has **no serde derives**, so credentials structurally cannot reach persisted records; recorded origins are credential-free.
- **Token transport discipline.** API calls carry the PAT only in the `Authorization` header (reqwest error Display can't leak it via URL); diagnostics probe uses headers; the metadata-branch push uses libgit2 `Cred::userpass_plaintext` (in-process, never in argv or URLs); git CLI auth rides `http.<url>.extraheader` env with registered sensitive values and `redact_auth_url` on every error path; `GitCloneStarted/Completed` events carry only credential-free URLs; `ForgejoContext` redacts in `Debug`.
- **Authz parity.** All `/runs/{id}/pull_request*` handlers sit behind `RequireRunScoped`; `/repos/forgejo/{owner}/{name}` behind `RequiredUser`; integration status exposes only the instance URL. Merge/close act on the stored link's coordinate — identical trust model to the pre-existing GitHub endpoints.
- **Admission/preflight gates.** Forgejo targets without a configured integration or vault token are refused at intent admission (422 with remediation) and reported in preflight; `FORGEJO_TOKEN` env injection into runs is gated on the run origin matching the instance, and forgejo runs deliberately skip GitHub credential acquisition.
- **Supply chain and secrets.** No new external runtime dependencies (only dev-only `httpmock 0.8`); no committed secrets; the live contract test reads everything from env. The SQLite migration is additive with a CHECK constraint; all store queries are parameterized; legacy rows default to the GitHub provider.

The one thing I'd ask the implementer to pick up is finding 1 — it's a two-line fix. Findings 2 and 3 need no action beyond what's already documented.
