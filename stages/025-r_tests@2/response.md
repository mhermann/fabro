# Test coverage review — Forgejo integration (111 files, +5637/−464)

## Blocking: the `fabro-sandbox` test suite does not compile

The review-fix stage fixed the three stale struct literals in `fabro-workflow` but missed the entire `fabro-sandbox` crate. Since its test modules never compiled, none of the sandbox forgejo wiring has ever executed under test. Four distinct break sites, all verifiable by reading (signature vs. call arity):

1. **`src/push_credentials.rs`** — `build_token_source` now takes 3 args (`github_app, forgejo, clone_origin_url`); `token_source_requires_managed_credentials_and_a_github_origin` still calls it with 2.
2. **`src/clone_source.rs`** — `decide_clone` now takes 6 args (trailing `forgejo_instance_url`); every call in the test module passes 5. Worse: `non_github_origin_fails_without_skip_clone` asserts the error contains `"GitHub repository origins only"` — the new production message is *"support GitHub repository origins **and repositories on the configured Forgejo instance**"*. Even after fixing arity this test fails. The old contract test was left in place and **no test was written for the new contract**: forgejo-origin → `CloneDecision::Forgejo`, forgejo-origin without an instance → error, non-instance origin → new error, `forgejo_repo_layout` owner/repo mapping, `repo_cloned_for_record` returning `Some(true)` for forgejo.
3. **`src/sandbox_spec.rs`** — three `SandboxSpec::Docker { … }` literals omit the new `forgejo` field.
4. **`src/docker.rs` / `src/daytona/mod.rs`** — `DockerSandbox::new` (8 params), `with_docker_client` (9), and `DaytonaSandbox::new` (9) all gained `forgejo`; the test-module constructors still pass the old arity.

The Docker forgejo clone path (PAT-embedded URL via `fabro_forgejo::embed_token_in_url`, forgejo layout, post-clone `set-url`) consequently has zero executed coverage at any level.

## Specific untested behaviors

1. **Runner credential coexistence — the highest-value missing test.** `requires_forgejo_credentials` (runner.rs) is origin-blind: it fires for *any* non-dry-run clone-based run, and `maybe_build_github_credentials` then returns `None` whenever a forgejo context was built. Two untested cases with concrete consequences: (a) a **GitHub-origin** run on a server with forgejo configured + `FORGEJO_TOKEN` in the vault silently loses GitHub credentials (breaking the coexistence model the human chose); (b) forgejo enabled with **no** vault token makes `build_forgejo_context` return `Err`, which `?`-propagates — every clone-based GitHub run fails at startup. Neither has a test.
2. **Server PR endpoints.** `get/merge/close` forgejo paths in `handler/pull_requests.rs` (~205 added lines) have no test anywhere — not in `src/server/tests.rs` (mechanical field updates only), not in `tests/it/`. E.g. merging a forgejo PR against a mock instance, and the "origin does not match the configured instance" 400, are unexecuted.
3. **Repo-picker endpoint and integration status.** `/repos/forgejo/{owner}/{name}` and `forgejo_integration_status` (system.rs) — zero tests; `settings-integrations.test.tsx` only adds a *disabled* forgejo row to a fixture. No test for the configured / token-missing states on either side.
4. **Automation store provider round-trip.** Migration `2026091001` adds `target_provider`/`workflow_source_provider`; `store.rs` defaults legacy NULL → GitHub. `tests/store.rs` got only mechanical `provider: Github` edits — no test persists a **forgejo** target/workflow-source and reads it back, and none pins that a legacy NULL-provider row deserializes as `Github` (the compatibility claim the comment asserts).
5. **Web automation form.** `automation-form.tsx` (+41: provider select gated on `forgejoConfigured`, `provider` in the submitted target), plus automations-new/edit; `automation-form.test.tsx` untouched — nothing asserts a forgejo selection reaches `targetFromFormValues` output or that the picker hides when unconfigured.
6. **Preflight failure branches.** Only missing-token and happy path are tested. `run_forgejo_repository_access_check`'s repo-not-found (`Ok(None)`), branch-missing ("branch 'x' does not exist on the remote"), and origin-not-on-instance branches are untested — the branch-missing case is the boundary a user will actually hit.
7. **Metadata-writer forgejo branch.** `build_metadata_writer`'s forgejo path (normalized instance URL, `ForgejoStaticAuthProvider`, `fabro` username on push) has no test; the existing factory test only covers github normalization and the gitlab skip.
8. **Reducer boundary.** `run_state.rs`: a `PullRequestCreated` event with `provider: forgejo` → forgejo link projection is untested; neither is `provider: forgejo` with `origin: None`, which `unwrap_or_default()` turns into an **empty-origin** link that would later fail origin matching in the endpoints.
9. **Minor:** forgejo auto-merge warn-and-skip (`enable_auto_merge_if_requested`) — no test that a forgejo request with `auto_merge` set calls nothing and doesn't fail; pipeline reconcile reusing an existing open forgejo PR; config `normalize_forgejo_instance_url` **silently upgrades `http://` → `https://` for non-loopback hosts** — operator-visible behavior where only the loopback exception is tested.

## What is adequately covered

Said plainly: the client and types layers are well covered. `fabro-forgejo` has 12 httpmock tests asserting the wire contract (token-auth header, request bodies incl. the WIP prefix and `do` merge field, status→error mapping, reconcile matching) plus a live contract test; URL parsing/normalization/redaction has focused unit tests; `fabro-types` pins wire-default GitHub omission, legacy deserialization, and `validate_with_scm` for both providers and both error types; `fabro-api` adds the required type-identity + JSON-parity round-trips; config covers absent/normalize/loopback/enabled-without-url; manifest covers provider casing, missing-instance error, and the github lane; server admission covers both 422 paths and preflight happy/missing-token with probe assertions; the materializer tests instance threading and auth pairing; the PR-pipeline create test is genuinely behavior-level (asserts zero GitHub calls); repo/init is covered e2e via the generated project.toml. The existing tests that were updated are mostly behavior- rather than implementation-coupled — the problem is the holes named above, foremost that one whole crate's suite is unrunnable.
