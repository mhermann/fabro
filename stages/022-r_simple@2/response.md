Review complete. The change is largely disciplined — the accepted parallel-crate architecture, the inert webhook route, the twin harness, the threading hops, and the install/doctor surfaces all match what was decided, and I found no speculative abstraction beyond it. But there are six genuine complexity findings, two of them worth acting on.

## Findings

**1. `lib/apps/fabro-cli/src/commands/pr/link.rs` — client-side forge classification duplicates what the server already returns.** `forgejo_link_for_url` re-parses the URL, opens the CLI secret store, resolves `FORGEJO_URL`, and re-parses against the instance — all before the server call, all to choose the printed label `forgejo #7` vs `github #7`. But the server's link response already carries this: `fabro-api/build.rs` replaces the schema type with `fabro_types::PullRequestLink` (build.rs:560), which now has `forge`, and that is exactly the `record` type imported here. Delete `forgejo_link_for_url` and write the label from `record.forge.is_some()`. This removes ~20 lines, a per-invocation vault open, and a real inconsistency: if the CLI's `FORGEJO_URL` differs from the server's configured instance, the label says "github" for a link the server correctly stored as Forgejo.

**2. `lib/apps/fabro-cli/src/shared/forgejo.rs` — `build_forgejo_config`'s `settings: Option<&ForgejoIntegrationSettings>` parameter is dead.** Both call sites pass `None` (runner.rs:149, with a comment explaining workflow settings carry no server section; and `resolve_forgejo_config`:53). The settings-URL branch and the `settings.is_some_and(|s| !s.enabled)` check are unreachable. Drop the parameter; the function reads `FORGEJO_URL` env only. (Unlike `build_github_credentials`, whose settings-derived params are genuinely used, nothing here can ever supply `Some`.)

**3. `lib/components/fabro-forgejo/src/lib.rs` — `ForgejoRepository` is write-only.** Its only production caller, `forgejo_repository_access_check` in `run_manifest.rs`, discards the value (`get_repository(...)?.ok_or_else(...)`); `full_name`, `private`, and `fork` are read nowhere in the repo. The struct's only function is validating that a 200 body is repo-shaped. Simpler: `get_repository` returns `anyhow::Result<Option<()>>` and parses a private single-field struct internally; delete the public struct and its fixture maintenance. Same class: `ForgejoPullRequest`, `ForgejoPrUser`, `ForgejoPrRef` are `pub` with zero external consumers (grep confirms) — they can be private, since `get_pull_request` returns `PullRequestGithubDetail`.

**4. `lib/components/fabro-forgejo` — `chrono` is an unused dependency.** No `chrono` reference anywhere in the crate. Delete the Cargo.toml line.

**5. `fabro_forgejo::ssh_url_to_https` is `pub` with no external caller.** Its only caller is `normalize_forgejo_origin_url` inside the crate. GitHub's same-named function is used across four crates; this export is dead surface. Make it private.

**6. `lib/components/fabro-sandbox/src/docker.rs` (~1899–1920) — the `CloneDecision::GitHub` and `CloneDecision::Forge` arms are copy-paste identical except for the `CloneOrigin` tag.** Daytona already merged them (`CloneDecision::GitHub { .. } | CloneDecision::Forge { .. }` plus an `is_forge_origin` boolean, with a comment saying the sequences are identical). Docker should do the same — one arm, `CloneOrigin` chosen by the boolean. ~13 lines collapse to one. Minor adjacent wart: `ExistingPullRequest.node_id: String` uses `String::new()` as a "no node_id" sentinel for Forgejo; `Option<String>` would say what it means, though the comment does explain it.

## Checked and deliberately left alone

- The origin-normalizer pipeline (`ssh_url_to_https` / `strip_https_credentials` / `normalize_https_host_path` / `normalize_forgejo_origin_url`) is a near-copy of `fabro-github`'s, as are the `HttpClient`/`HttpResponse`/`MockHttpClient` trio. This is the duplication the human explicitly accepted with the additive-crate answer; extraction would touch `fabro-github`'s surface. On record, not a defect.
- The inert webhook route, the parallel `forgejo` fields threaded through StartOptions/StartServices/PublishOptions, the two dispatch enums (`PullRequestHost` in workflow, `PreparedPullRequestHost` in the server handler — different error shapes), the `ForgejoSandboxConfig` alias (13 local uses, documented), the twin (1.85k lines vs twin-github's 4.8k, including a real git-http-backend CGI path needed to exercise actual clones), and the install/doctor/diagnostics additions are all in the answered scope and proportionate.

Fixing 1–4 deletes code; 5–6 are one-line collapses. Nothing requires reworking the architecture.
