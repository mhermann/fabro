## 1. Repository structure, language, tooling, and where the change would land

**Stack:** Rust workspace (edition 2021, ~45 crates under `lib/apps`, `lib/components`, `lib/foundation`, plus `test/twin/*` test doubles), one React 19/Bun web app (`apps/fabro-web`), a generated TS Axios client (`lib/packages/fabro-api-client`), and Mintlify docs (`docs/public`). A new Forgejo integration would most naturally land as a **new component crate (e.g. `fabro-forgejo`)** mirroring `fabro-github`, plus touches in types, settings, server, sandbox, workflow, tracker, install, CLI, OpenAPI, twin-tests, and docs — or alternatively as a **provider abstraction** extracted under the existing `scm` config concept.

## 2. Goal restated, concretely

> Let Fabro operate against a **self-hosted Forgejo instance** (a Gitea fork; API at `<instance>/api/v1`) the way it operates against GitHub today: a user can configure Forgejo credentials in settings/vault, run workflows whose git origin points at the Forgejo instance (clone-based Docker/Daytona sandboxes accept it), get per-run tokens injected, have runs open/merge/close pull requests on Forgejo, optionally receive Forgejo webhooks to trigger automations, and manage connection status/diagnostics from the web UI — with docs and tests mirroring `docs/public/integrations/github.mdx` and `test/twin/github`.

Forgejo platform facts I verified against current docs: API base is `<instance>/api/v1` (self-hosted, must be configurable); auth is PAT (`Authorization: token ...`), OAuth2 tokens (`Bearer ...`), or basic auth — **there is no GitHub-App-style RS256-JWT → installation-token endpoint**; "Authorized Integrations" (JWT/OIDC, JWKS-validated) exist but target CI-issued tokens, not a hosted server minting scoped tokens. REST endpoints are Gitea-shaped (`/repos/{owner}/{repo}/pulls`, merge via `POST .../pulls/{index}/merge` with `Do` field) — *not* byte-identical to GitHub (different paths, methods, payload field names, pagination).

## 3. What I now know for certain

- The integration is **deep and load-bearing**: `fabro-github` has 6 dependent crates; origin parsing, run admission, sandbox cloning, PR lifecycle, token minting/refresh (with provenance and replication-lag retry), webhooks, OAuth login, install wizard, diagnostics, and system-integration status are all GitHub-specific today.
- There is an **existing seam for multi-SCM**: `RunScmSettings { provider: Option<String>, owner, repository, github: Option<ScmGitHubSettings> }` in run settings (also in the OpenAPI spec), and `RepositoryProvider::{Github, Git, Unknown}` — i.e., the codebase already anticipates named SCM providers even though everything below it assumes GitHub.
- `GITHUB_BASE_URL` env override already exists in `fabro-github::github_api_base_url()` (used by tests/diagnostics) — but the URL grammar (`parse_github_owner_repo`) is hard-coded to `github.com` hostnames, so it alone can't target a Forgejo instance.
- Clone-based providers (Docker, Daytona) **explicitly reject non-GitHub origins** (`clone_source.rs` error message; CLAUDE.md documents "GitHub-only clone-source contract"). Daytona clones via its SDK with `owner/repo` + GitHub credentials.
- Secrets flow: vault-backed (`fabro-install` writes `GITHUB_*` keys), with a registry of secret env names (`fabro-static/src/secret_registry.rs`) and scrubbing policy.
- The test architecture expects a **twin server** per external dependency (`test/twin/openai`, `test/twin/github` with fixture-driven handlers + git smart-HTTP), and strategy docs (`docs/internal/`) constrain events, errors, testing, secrets, migrations, and API type ownership — all apply to this feature.
- Auth model: browser login via GitHub OAuth (`ServerAuthMethod::Github`, `github_endpoints.rs`, `/login/oauth/*` + `/user`), distinct from the repo-integration credential strategy (`token` vs `app`).
- Webhook ingestion is one route (`/api/v1/webhooks/github`) authenticated by HMAC-SHA256 `X-Hub-Signature-256`, feeding automations via `automation_materializer.rs`.
- Forgejo specifics (from official docs, v16): `/api/v1` base, `token`/`Bearer`/basic auth, OAuth2 provider present, pagination `page`/`limit`, OpenAPI published at `/swagger.v1.json`; no installation-token equivalent.

## 4. Genuinely ambiguous — where two engineers would build different things

1. **Scope of parity.** Full GitHub parity (clone, run token, PRs, webhooks, OAuth login, tracker, install wizard, diagnostics) vs. the pragmatic core (PAT auth + clone + PR lifecycle)? "Similar to github integration" doesn't say. GitHub Projects V2 tracker almost certainly has **no Forgejo equivalent** (Gitea/Forgejo projects lack a public GraphQL API).
2. **Auth model mapping.** GitHub has App (JWT → scoped installation tokens, the basis of `GITHUB_TOKEN` minting and `token_source.rs` refresh logic) vs. PAT. Forgejo only has PAT/OAuth2. Do we: (a) support only a static PAT (simplest; kills the per-run scoped-token feature), (b) map to Forgejo OAuth2 tokens, or (c) attempt "Authorized Integrations" JWT (JWKS-hosting required — Fabro would have to run an OIDC issuer, a big new surface)?
3. **Instance URL model.** One Forgejo instance configured globally (server-level, like `[server.integrations.forgejo] url = "..."`), or resolved per-repo-origin (any host that isn't github.com)? And how do run origins get classified — does `RepositoryProvider` grow a `Forgejo` variant, and is that by configured-instance match or URL heuristics? Affects `GitHubRepositorySlug`, `PullRequestLink` (currently hard-coded to `github.com` URLs), DB-stored data, and the API schema.
4. **Architecture: sibling crate vs. provider abstraction.** A `fabro-forgejo` crate next to `fabro-github` (fast, parallel, but duplicates and pushes `if provider == …` branching into server/workflow/sandbox), vs. extracting a `ForgeProvider` trait (e.g. parse origin / resolve clone creds / create PR / merge PR) that both implement — a large refactor of `fabro-github`'s public surface (`GitHubContext`, `GitHubRepositoryAccess`, `InstallationTokenSource`) that touches every dependent crate. Also: does `token_source.rs`'s refresh/provenance machinery get reused for static Forgejo PATs (it already has a `Static` provenance) or forked?
5. **API-shape translation.** Gitea-family REST differs in details (merge endpoint method/fields like `Do`, token header `token` vs `Bearer`, pagination, PR JSON schema differences feeding `PullRequestGithubDetail`). Do we translate into existing GitHub-shaped types (least churn, risk of semantic drift — e.g. no token expiry, no auto-merge API) or introduce provider-tagged PR detail types? Note CLAUDE.md's rule against `ApiFoo` adapter-smell types cuts both ways here.
6. **Webhooks.** Forgejo/Gitea webhooks use different payload shapes ("gitea" event type) and signature headers (needs verification: `X-Gitea-Signature` vs `X-Hub-Signature-256`, which Forgejo also supports for "github"-type webhooks). New route `/api/v1/webhooks/forgejo`? Separate secret? Does the automation materializer understand both event grammars? Is the Tailscale-funnel/server-URL webhook strategy reused?
7. **OAuth login.** Is "sign in with your Forgejo account" (a *self-hosted* IdP — issuer/allowed-hosts config, trust questions, `AuthMethod`/`IdpIdentity` changes) part of this, or out of scope? Two reasonable answers.
8. **Multi-tenancy.** GitHub is a single global counterparty; Forgejo is many instances. Support exactly one configured instance, or several simultaneously (per-run origin decides)? Changes settings schema, vault keys (`FORGEJO_TOKEN`? per-instance?), and slug identity (owner/repo is no longer unique without the instance).
9. **Non-goals / adjacent providers.** Should the design generalize to Gitea itself (Forgejo is Gitea-compatible; codeberg.org is Forgejo) from day one, or hard-scope to Forgejo branding? `is_github_origin`-style host matching would then be wrong for one of them.
10. **Product surfaces.** Does the web install wizard, `fabro install forgejo` CLI, system integrations status card (`IntegrationProvider::Forgejo`), and OpenAPI/TS client updates all land in phase one, or is this a CLI/server-only feature initially? (The OpenAPI-first workflow makes each schema change ripple into conformance tests and the generated TS client.)

**Recommended clarifications before building:** (1) target scope (clone+PR core vs. full parity), (2) PAT-only auth for v1, (3) single configured instance vs. per-origin detection, (4) sibling crate with a thin shared trait vs. full provider abstraction. Everything else can follow from those four decisions.
