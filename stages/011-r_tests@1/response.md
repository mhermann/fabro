I've reviewed the full diff (96 files) with an eye on test coverage, reading the surrounding code for each test I cite. I also ran the new test suites where cargo was available — `fabro-forgejo` (22 tests), `fabro-types` (506), `fabro-manifest` (55) — all pass as written.

## What is adequately covered

The leaf layers are well tested, behavior-focused, and would fail if the code were wrong:

- **`fabro-forgejo` crate** (22 tests): auth header scheme (`Authorization: token`), exact wire bodies for create/merge/close (including capital-`Do` and `WIP:` draft), status-code mappings (401/404/405→`NotFound`/not-mergeable), `commit.id` branch heads, URL parsing (subpath installs, host-prefix attack `forgejo.example.com.evil.test`, extra path segments), token embedding with redaction assertion, credential-helper host scoping, base-URL trimming. The mock harness asserts headers and request bodies, not just responses.
- **`fabro-types`**: `PullRequestLink.forge` serialization shape, the legacy-byte-identical round-trip guarantee (a real backward-compat property), `/pulls` and `/pull` parsing, subpath instances, deserialize-time URL/instance validation; `is_forgejo_origin` host/path matrix including scheme-agnostic SSH forms.
- **`fabro-config`** (4 new tests incl. negative cases), **`fabro-manifest`** (forgejo origin build + hard error without `FORGEJO_URL`), **`fabro-api`** round-trips (legacy + forge JSON vs OpenAPI fixture), **web** (Forgejo row rendered and omitted-for-older-servers), **env-var registry** membership, and **`clone_source.rs`** (Forgejo `CloneDecision`, missing-instance failure, layout parity, provider dispatch).

## Findings — untested behavior, ordered by severity

**1. `PullRequestLink::from_stored_pr_url` has zero tests, yet it's now the sole reconstruction path for durable run-state PR links.** The function is new in this change (`fabro-types/src/pull_request.rs:148`) and `fabro-store/src/run_state.rs:390` now rebuilds the persisted link from the stored PR URL through it, with a silent fallback to a forge-less `owner/repo/number` when parsing fails. Concrete untested cases: (a) a stored `https://forgejo.example.com/acme/widgets/pulls/12` URL yields a link carrying `forge.base_url` — nothing verifies that run replay preserves the instance; (b) the `unwrap_or_else` fallback in `run_state.rs` (parse failure → forge-less link); (c) port-bearing instance URLs (`https://forgejo.example.com:8443/...`), which take the port-reconstruction branch no other test reaches. `from_forgejo_url` is tested, but `from_stored_pr_url` is a different algorithm (it *infers* the base URL) and shares none of those tests.

**2. No pipeline-level test for the Forgejo publish path.** `open_pull_request`'s GitHub branch has httpmock-based tests for reconciliation-on-failed-create, title composition, and error paths (`pipeline/pull_request.rs` tests module); the `PullRequestRemote::Forgejo` branch has none. Untested behavior: the Forgejo reconcile-after-failed-create flow, `pull_request_link()`'s forge mapping, the auto-merge no-op, and `publish.rs`'s remote selection — including the new error "pull request creation requires GitHub credentials for a GitHub origin" when a non-Forgejo origin lacks a GitHub app. An inverted match arm or a dropped `forge:` field would pass the entire suite. The harness is already available: `ForgejoContext::with_http_client` is public and httpmock is already a dev-dependency of this crate.

**3. `build_sandbox_env`'s Forgejo branch is untested** (`pipeline/initialize.rs`), even though the same test module was updated for the new signature. The untested cases: a Forgejo origin + creds inject `FORGEJO_TOKEN` *and* the instance-scoped `GIT_CONFIG_KEY_0` helper; a **GitHub** origin with Forgejo creds present must *not* receive the Forgejo credential helper — the helper unconditionally echoes `$FORGEJO_TOKEN`, so a wrong guard scope silently feeds a Forgejo token to github.com pushes. `merge_forgejo_bridge_env` itself also has no test (its sibling `merge_git_bridge_env` has both failure-path and contract tests).

**4. `build_token_source`'s Forgejo branch is untested** (`push_credentials.rs`). The existing test was updated only for arity. Untested: Forgejo origin + creds → `InstallationTokenSource::pat` (including that refresh resolves to the same static token); Forgejo creds + a github.com origin → not hijacked.

**5. `fabro install forgejo` has one test — a help-snapshot line — versus ~18 cmd tests for `install github`.** Untested: `--non-interactive` requires `--url`; `--non-interactive` requires `FORGEJO_TOKEN`; a failed token verification (`get_authenticated_user` 401) aborts **without writing settings or vault** — the command's load-bearing verify-before-persist property; success persists the vault secret and the settings URL.

**6. The `get_forgejo_repo` handler's string-sniffing is pinned by no test at either end** (`server/handler/system.rs`): it branches on `err.to_string().contains("not found")` and `contains("token rejected")` — coupling to `fabro_forgejo`'s rendered error text. The crate test for `get_repo` 404 asserts owner/repo and the base URL but never "not found", and no test asserts `get_repo`'s 401 message at all. A future rewording in the client silently converts `accessible: false` responses into 502 BAD_GATEWAY.

**7. Preflight's Forgejo routing is untested** (`run_manifest.rs`). The GitHub access check got an injectable `check_remote_ref` closure precisely so tests could drive it; the new `check_forgejo_remote_ref` / `run_forgejo_origin_check` call the real API with no seam, and every updated call site passes `None` for Forgejo creds. Untested: a Forgejo origin routes to the API probe rather than the GitHub ls-remote path, a missing branch fails preflight, and a configured instance without a token fails closed via the Forgejo check row (the `Ok(None) | Err(_) => None` swallow at the top of `build_preflight_report`).

**8. Smaller gaps:** (a) `validate_source_spec`'s new non-github fork rejection (`operations/fork.rs:131`) is untested — the path was already untested — and a test would have surfaced that the message "fork is not supported for Forgejo runs" is also emitted for plain-git (e.g. GitLab) origins, where it's misleading; (b) every Docker/Daytona e2e and workflow integration test change is a mechanical `None` — no test anywhere actually clones a Forgejo origin, so the composed clone environment (env var + helper + URL rewrite) is never exercised end-to-end; (c) `forgejo_integration_status` has no handler test, though this matches the existing (absent) coverage of `github_integration_status`.

## Verdict

Coverage is good at the leaves (client wire contract, URL/serialization parsing, config resolution) and thin exactly where Forgejo meets the existing GitHub machinery: run-state hydration, the publish pipeline, sandbox env/token wiring, preflight, the server PR routes, and the install command. Those middle-layer paths are where a regression would be silent, and the harnesses to test them (public `with_http_client`, httpmock, existing fixture helpers) are already in the tree. Items 1–5 are the ones I'd want closed before this ships; 6–8 are worth pinning but lower stakes.
