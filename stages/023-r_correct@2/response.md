# Correctness review — Forgejo integration (111 files, +5637/−464)

I read the full diff plus the surrounding context of every seam it touches. I could not execute anything (review-only checkout), so all findings below are from code reading; each has a concrete trigger. The overall architecture is sound and the wire/persistence back-compat is genuinely well done — but I found two defects I'd block on, and several smaller ones.

## Blocking

**1. CLI worker credential gate is origin-blind — breaks GitHub runs on dual-forge deployments and silently drops requested GitHub tokens.**
`lib/apps/fabro-cli/src/commands/run/runner.rs:1151-1175` — `requires_forgejo_credentials` (`:1173`) returns true for **any** non-dry-run clone-based run; it never checks the run's origin or `GitRunTarget.provider`, despite the doc comment claiming "when the run targets a forgejo-hosted repository." Two wrong results follow:

- **(a)** `[server.integrations.forgejo] url = "https://git.example.com"` configured, no `FORGEJO_TOKEN` in the vault, and a plain **GitHub-targeted** run with Docker/Daytona: `build_forgejo_context` (`shared/forgejo.rs:12-27`) hard-errors "FORGEJO_TOKEN not configured", the `?` at `runner.rs:142` aborts `execute`, and the run fails before starting. On `main` this run worked; the coexistence scenario the plan explicitly chose is broken in the CLI worker. The server path does this correctly — origin-gated lazy resolution at `server.rs:4188-4201` — so the two paths disagree.
- **(b)** Forgejo configured **with** token, run on a forgejo repo whose workflow declares `[run.integrations.github]` token request: `runner.rs:1125` `if forgejo_run { return Ok(None); }` short-circuits `maybe_build_github_credentials` *before* the `is_token_requested()` check at `:1182`, so `GITHUB_TOKEN` is silently absent from the workflow env where `main` would have supplied it.

**2. Forgejo git basic-auth username is inconsistent across the change — at most one spelling can be correct, and drift repair overwrites a working URL with the other one.**
The same PAT is sent with two different usernames:

- `fabro`: `fabro-forgejo/src/url.rs:135` (`embed_token_in_url`, used by the **Docker clone**, `docker.rs:962-975`), `git_checkout.rs:356` (`forgejo_git_auth`, server materializer clones), `run_metadata.rs:210-212` (metadata-branch git2 callbacks).
- `x-access-token`: **Daytona clone options** `daytona/mod.rs:1642-1648`, Daytona post-clone set-url `daytona/mod.rs:1817` (via `fabro_github::embed_token_in_url`), and the shared push refresh/drift embed `push_credentials.rs:204` and `:417` (also `fabro_github::embed_token_in_url`, which hardcodes `x-access-token` at `fabro-github/src/lib.rs:1396`).

Concrete failure: a Docker forgejo run whose push auth fails as `fabro:<PAT>` triggers auth-shaped drift repair (`sandbox.rs:1961` → `ensure_embedded(force=true)` → `set_url_via_exec`), which rewrites `origin` to `x-access-token:<PAT>` — actively replacing the remote with the *other* unverified spelling. And every Daytona forgejo clone authenticates as `x-access-token:<PAT>` (`GitCloneOptions`), a spelling that appears nowhere else in the forgejo paths. If the instance requires the token owner's real username with the PAT as password — the convention the docs' `write:repository` setup implies — **neither** spelling works and `ForgejoContext` carries no username to fix it; `docs/public/integrations/forgejo.mdx` documents no username requirement at all, and the forgejo E2E coverage is API-only (`token` header), never git-over-HTTP basic auth. Whatever the server's rule is, this needs to be one deliberate, documented convention.

## Non-blocking

**3. `fabro validate` / `fabro graph` / `fabro preflight` regress on forgejo-scm repos even with the instance configured.** `preflight.rs:34`, `graph.rs:41`, `validate.rs:24` all build `ManifestBuildInput` with `forgejo_instance_url: None`; `configured_repo_origin_url(settings, None)` is now a hard error for `provider = "forgejo"` (`fabro-manifest/src/lib.rs`), so these commands fail with "requires a configured Forgejo instance" on a repo where the server's `fabro_run_create` path (`run_tool_manifest.rs:44`, which does pass the URL) succeeds. On `main`, the unknown provider was ignored and the commands worked. The CLI demonstrably has settings access (`repo.rs`, `doctor.rs` load it).

**4. Sub-workflow stage drops `FORGEJO_TOKEN` but keeps the GitHub token.** `handler/manager_loop.rs:260` passes the parent's `github_token` to the child's `StartServices` but hardcodes `forgejo_token: None`. A workflow reading `FORGEJO_TOKEN` inside a sub-workflow on a forgejo run gets nothing, while the GitHub equivalent inherits the parent's source.

**5. PR link endpoint accepts any host as a "forgejo" link.** `pull_request_link_from_url` (`fabro-types/src/pull_request.rs:231-239`) falls back to the forgejo parser for *every* non-github.com host, and `pull_request_record_from_link_request` (`handler/pull_requests.rs:68-79`) performs no instance check — `POST /runs/{id}/pull_request` stores `provider: forgejo, origin: https://anything.example` from `https://anything.example/a/b/pulls/7`. It's inert (merge/close/get later 400 "origin does not match"), but GitHub links are host-constrained at this same seam. Related: deferred creation stays GitHub-only (`RunPrInputs::extract` rejects forgejo origins, supervisor passes `forgejo: None` — consistent, since the enqueue gate blocks forgejo first), so a forgejo run whose in-line PR creation failed cannot be retried via `POST /pull_request/creation`.

**6. Nits:** `cache_namespace` doc says "scheme and port stripped" but only the scheme is (`automation_materializer.rs:262-271` — behavior is still collision-safe); `server.rs:4192-4200` origin-matches against `forgejo.url` ignoring `enabled` while preflight uses `instance_url()` (divergent, but fails closed because `forgejo_context` returns `Ok(None)`); `retry.rs:175` and `git_checkout.rs:919` test literals have broken indentation (rustfmt).

## Verified correct (checked, not assumed)

Wire back-compat is right: `ScmProvider` defaults to `github` with `skip_serializing_if`; `PullRequestLink` keeps the historical 4-field GitHub shape, rejects forgejo-without-origin and github-with-origin, cross-checks `html_url`, and strips embedded credentials from forgejo origins; event props are additive with serde defaults; the automation migration is nullable with a CHECK and reads NULL as GitHub; `build.rs` already mapped `GitRunTarget`/`PullRequestLink` via `with_replacement` and parity tests pin type identity. Admission fails closed (422 `forgejo_integration_unconfigured`, `handler/runs.rs`); the materializer threads the instance URL correctly with the per-forge bare-clone namespace; `decide_clone`, `ScmTarget::resolve`, and `publish`'s resolve-before-credentials ordering are consistent; config resolution (loopback `http` allowance, template demotion, explicit error when enabled without URL) is sound; `FORGEJO_TOKEN` sits in the secret registry and is redacted; the supervisor can only ever receive GitHub runs (the enqueue gate is the only producer of pending creations); the forgejo client's endpoint shapes (`/api/v1`, `token` header, `Do` merge field, issues-endpoint close, `commit.id` branch SHA, client-side reconciliation match, `WIP: ` drafts) match the Gitea-compatible API.

Findings 1 and 2 are the ones I'd hold the change for: 1 is a functional regression for the coexistence case the design chose, and 2 leaves the flagship write path (clone → push → PR) with credentials whose validity depends on which of two mutually exclusive spellings a given code path happened to pick.
