I attacked the plan against the repository as it actually is. Most of it holds: the addressing mechanism (`provider` on `GitRunTarget`), the `with_replacement` flow for the wire types, the parallel-crate structure, the sandbox clone split, and the OpenAPI-first ordering all match how this codebase really works. Three attack vectors came back empty: `git.rs` only uses `fabro_github::normalize_repo_origin_url` for display sanitization (its push functions are URL-generic, so token-embedded forgejo URLs pass through untouched); `diagnostics.rs` is a deeper health probe whose absence is additive-later, not wrong; and `deny_unknown_fields` on `GitRunTarget` only bites on downgrades, which the repo doesn't promise.

Two defects are real:

**1. Hidden coupling: the plan ignores `[run.scm] provider`, which already exists and already branches on provider.** `fabro-manifest/src/lib.rs:434` (`configured_repo_origin_url`) reads `[run.scm]` and returns `None` unless `provider` is unset or `"github"` (line 436–442: `is_none_or(|provider| provider.eq_ignore_ascii_case("github"))`). This is the settings-pinned repo path — resolved from user/project/workflow layers for both CLI and server runs — and it's one of the producers of run-target repos that tier (b) claims to cover. The plan touches this exact file (item 38) for origin observation but never mentions this function. If missed, a user who sets `[run.scm] provider = "forgejo" owner/repository` gets **silent** degradation (the function returns `None`; no error, no repository configured), which none of the plan's automated checks would catch. The fix is small but must be in the plan: extend `configured_repo_origin_url` to accept `"forgejo"`, derive `{forgejo_url}/{owner}/{repo}`, and produce a forgejo-provider target — which also answers how the plan threads the instance URL into `fabro-manifest` beyond the origin-observation path.

**2. Verification for the headline tier-(b) surface is optional-only.** Every automated check in the plan (per-crate nextest, conformance, clippy, bun) passes even if the server-side forgejo run path (validate → preflight → clone → PR) is entirely broken, because existing tests are github-shaped and new unit tests test functions in isolation. The one check that would catch it — the manual Docker Forgejo round-trip — is explicitly marked "optional". Tier (b) is the human's chosen scope; its core path needs at least one automated test that would fail if the wiring is wrong, e.g. a mock-`HttpClient` integration test for `run_manifest` preflight with a forgejo-targeted run (the pattern exists in `fabro-github`'s `tests_mock` and server tests), or promoting the Docker round-trip from "optional" to a required gate for the stage.

Advisory (not blocking, but cheap to fold into the same revision): add `git.rs`, `sandbox_git.rs`, `diagnostics.rs`, and `fabro-cli/src/commands/repo/init.rs` to the step-23 audit list so the implementer greps them deliberately rather than by luck.

Both blocking defects are fixable with a text-level plan revision; no design decision needs revisiting.
