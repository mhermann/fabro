I verified the plan's riskiest claims against the code. Three blocking defects, all in the same spine — how a forge target acquires its origin URL and credentials:

**1. The worker credential layer is the wrong file, and the right one is missing.**
The plan asserts (Phase 4, item 20) that the worker reads `FORGEJO_TOKEN` "from the vault via `FABRO_HOME`/storage paths already allowlisted" and changes nothing in `spawn_env.rs`. The actual mechanism: the worker process is the CLI's `__run-worker` mode, and credentials are built in **`lib/apps/fabro-cli/src/commands/run/runner.rs`** — `load_worker_vault(&storage_dir)` then `maybe_build_github_credentials(&run_spec.settings, &vault_guard)` (lines ~139–142). The GitHub App PEM reaches the worker via env (`worker_runtime.rs:104`) precisely because the *PAT/App split* is resolved worker-side from the settings snapshot + vault. The plan lists neither `runner.rs` nor `maybe_build_github_credentials`. Without a `maybe_build_forgejo_credentials` twin there, no PAT ever reaches `initialize.rs`, the sandbox, or the PR pipeline — every forgejo run fails at clone time, and the failure surfaces only at integration, after Phases 4–6 are built on top of nothing.

**2. `automation_materializer.rs` is unlisted and would clone from the wrong host.**
Automations are a first-class `GitRunTarget` producer: `AutomationRunMaterializer` holds `target: GitRunTarget` (lines 22/32), calls `GitRunTarget::validate` (line 241), and resolves remotes via `ServerGitHubRemoteResolver` → `git_checkout::github_clone_url(repo)` — i.e. `https://github.com/{owner}/{repo}.git` built from the bare slug (lines 153–167). A forgejo-declared automation under this plan compiles, validates, then clones from github.com. The plan's file list claims to cover the server's GitHub consumers; this one is missed.

**3. The forge→origin seam is specified in a way that won't compile as written.**
- Phase 1 item 5 says forge targets make `validate()` "return a slug-only projection" — but `ValidatedGitRunTarget.git: GitContext` is **non-optional**, and `GitRunTarget::validate` is called from at least `run_compiler` and `automation_materializer` (line 241), not one admission point. Either `validate` grows a forge-base input (signature change at every caller) or every caller overwrites `git` post-validate — the plan must pick one, because "slug-only" doesn't type-check.
- Phase 7 item 33 says `configured_repo_origin_url` returns "a sentinel descriptor (not a URL)" — but its return value is fed **directly into `GitContext.origin_url`** in `inspect_local_git` (`fabro-manifest/src/lib.rs:382-404`). A non-URL sentinel corrupts the legacy git context. The workable shape is the opposite: for a declared forgejo run, keep the local remote's real URL as `origin_url` and carry `forge: Some("forgejo")`, with the server cross-checking the remote host against its configured instance at admission.

Defects 1 and 2 are missing files in the credential/target spine; defect 3 is the same spine specified contradictorily. Together they'd force a redesign mid-implementation across `run_intent.rs`, `fabro-manifest`, `run_compiler.rs`, `automation_materializer.rs`, and `runner.rs` — exactly the rework a plan exists to prevent. One focused revision fixes all three; everything else (phasing, OpenAPI flow, sandbox/publish/webhook boundaries, verification, non-goals) is sound and unchanged.
