Three blocking defects, each verified against the repository rather than inferred. Everything else held up under attack.

## Defect 1: The worker env allowlist makes in-cluster deployment fail, and the plan forbids the fix

The plan states "no worker env-allowlist changes" and claims "in-cluster SA: accessible via filesystem, no env needed." That is factually wrong for kube-rs: in-cluster client discovery is **gated on `KUBERNETES_SERVICE_HOST` / `KUBERNETES_SERVICE_PORT` env vars** — without them `Client::try_default()` falls through to kubeconfig discovery, which doesn't exist in a pod.

Sandbox construction happens in the **spawned worker process** (`fabro-workflow::operations::start` is the run-execution path; `fabro-server/src/spawn_env.rs` `apply_worker_env` runs `env_clear()` plus the narrow allowlist — PATH, HOME, FABRO_*, AWS identity vars… no `KUBERNETES_*`). So in the flagship deployment — Fabro server running in-cluster, workers spawned with a scrubbed env — every Kubernetes run fails at `SandboxSpec::build` with "no kubeconfig found" while the server-side registry works fine. The repo has exact precedent for the fix: the AWS SigV4 chain vars were added to `WORKER_ENV_ALLOWLIST` precisely because "Bedrock re-resolves from the ambient chain… must survive `env_clear()`." `KUBERNETES_SERVICE_HOST` is already a registered constant in `fabro-static/src/env_vars.rs:125`. The plan must add `KUBERNETES_SERVICE_HOST`/`KUBERNETES_SERVICE_PORT` to the allowlist and drop the "allowlist unchanged" claim.

## Defect 2: The random per-pod agent token breaks reconnect, which is a load-bearing flow

The plan: "Bearer-token auth (per-pod random token generated by the provider)." The token exists only in the creating process's memory. But `reconnect.rs` exists precisely to reattach **from a different process or after a restart**: server-side file-browser/exec endpoints reconnect to live run sandboxes (`run_files.rs`, `handler/sandbox.rs` via `reconnect_for_run`), and runs resume from persisted `RunSandboxInstance` records after restarts. After any server restart, the provider cannot authenticate to the agent of a still-running pod — file access, exec, and resume are dead until the pod dies. Docker needs no token; Daytona's credential lives in the vault. The repo already has the pattern for exactly this problem: `WorkerTokenKeys::from_master_secret(SESSION_SECRET)` derives stable tokens from a vault master secret. The plan must either derive the agent token deterministically (HMAC over pod name + vault master secret, mirroring `worker_token_keys_from_server_secrets`) or drop pod-internal auth entirely (defensible: port-forward access is already RBAC-gated and the user's own processes share the pod). Random-per-pod is the one option that is wrong.

## Defect 3: The default agent image ref points at an image nothing publishes

Default `ghcr.io/fabro-sh/fabro-sandbox-agent:<version>` plus a local-only `cargo dev agent-image` command means every non-developer user's first Kubernetes run fails with ImagePullBackOff. The human accepted "Fabro publishes an agent image" as part of the sidecar answer — publishing is in scope, not quietly added. The plan must wire the agent image into the release path (extend `cargo dev release`/the release pipeline alongside `docker_build.rs`, or explicitly state the release-work item), otherwise the feature ships broken-by-default and the omission is discovered only post-merge.

## Non-blocking findings (for the implementer, not worth a round)

- `clone_source.rs`, `from_environment.rs`, and `managed_labels.rs` `#[cfg]` gates all need `kubernetes` added — the plan's "compiler-driven completeness" covers this; fine.
- Docker's `clean_bash_env_entries` is private to `docker.rs`; the K8s provider must move or duplicate the BASH_ENV scrub for the agent's exec env — ordinary judgment call.
- Completed-run sandboxes won't be browsable (stop deletes the pod) unlike Docker — this was stated in the answers round and accepted; just document it prominently.
- `sandbox_details()` has a catch-all arm, so the run-details tab can defer; only the inventory pod→`SandboxInfo` mapping is required for step 5.
- One `k8s-openapi` version feature must be selected when adding the dep — mechanical.
- Terminal/file tabs in the web UI will surface the explicit "not supported" errors for K8s runs — consistent with the agreed scope.

Defects 1 and 2 would each produce work that has to be redone (a deployment mode that cannot function; an auth scheme baked into the agent protocol that must be redesigned after the first restart test). Defect 3 ships a broken default. All three are one-line-to-few-line plan amendments, but they change what gets built.
