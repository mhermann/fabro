Sandboxes isolate agent execution from the host machine. When an agent runs a shell command, edits a file, or searches code, it does so inside a sandbox — preventing unintended side effects on the host and providing a reproducible environment for each run.

Fabro supports four sandbox providers: `local` (no isolation), `docker` (container-level), `daytona` (cloud VM), and `kubernetes` (pod-per-run on a Kubernetes cluster). See [Environments](/execution/environments) for full provider-specific configuration.

Operators can enable or disable which providers the server may launch with
`[server.sandbox.providers.<provider>]` in `settings.toml`. Missing entries default to
`enabled = true`; setting `enabled = false` rejects new runs whose effective provider is disabled.
Dry-run Docker/Daytona/Kubernetes runs execute locally, so they are governed by the `local` provider policy.

The API can also list Fabro-managed sandboxes directly from configured providers:

```http
GET /api/v1/sandboxes
GET /api/v1/sandboxes/{id}
```

Provider-backed inventory is useful when you need to inspect Docker, Daytona, or Kubernetes resources independent of a single run projection. Listing is fail-soft: available provider results are returned with provider errors in response metadata.

## Kubernetes provider

The Kubernetes provider creates one pod per run (`fabro-<run-id>`) in a single
namespace and executes agent commands through the Kubernetes exec API.

- **Connection** is inferred with kube-standard rules: the in-cluster
  ServiceAccount when running inside a cluster, then `KUBECONFIG`, then
  `~/.kube/config`. The namespace is the one the resolved context (or
  ServiceAccount) points at — there are no Fabro-specific Kubernetes settings
  or secrets beyond `enabled`.
- **RBAC** must allow, in the target namespace: `create`/`get`/`list`/`delete`
  on `pods`, `create` on `pods/exec`, and `create`/`delete` on `networkpolicies`.
- **Network modes** are enforced with a per-pod `NetworkPolicy` (owner-referenced
  to the pod, so both are garbage-collected together). Enforcement depends on
  the cluster CNI supporting `NetworkPolicy`; on a cluster without it, `block`
  and `cidr_allow_list` policies are created but not enforced.
- **Stopping** a Kubernetes sandbox deletes its pod. A paused-and-resumed run
  recreates the pod from the checkpoint instead of reusing it; image references
  must be pullable from the cluster (pull secrets come from the namespace's
  ServiceAccount `imagePullSecrets`).

## Network access control

For cloud sandboxes (Daytona and Kubernetes), you can control outbound network access with `[environments.<slug>.network]`. Three modes are available: `"allow_all"` (default), `"block"`, and `"cidr_allow_list"` with an `allow = ["..."]` CIDR list.

Server defaults in `settings.toml` apply when a run config doesn't specify `network`. Individual run configs can override the server default.

See [Environments — Network access](/execution/environments#network-access) for syntax examples and the full reference.
